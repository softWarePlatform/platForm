# 压力测试原始结果与分析

## 1. 结论

2026-09-03 在同一台 Windows + Docker Desktop Kubernetes 主机上，对单体入口与最终微服务入口使用同一脚本、同一数据规模、同一并发参数完成了各 3 轮重复测试。三个接口合计每种架构 270 次请求，全部成功，错误率均为 0。原始 JSON 保留了每个请求的状态码和耗时，未只保留汇总值。

本次低并发、短时实验中，微服务入口的三项指标中位 QPS 均高于单体，且平均响应时间/P95 更低；该结论只适用于本次机器、数据集和参数，不能外推为生产容量结论。

## 5. 原始证据与复测

- `raw-results/perf-monolith-20260903.json`：单体 3 轮逐请求原始结果；
- `raw-results/perf-microservices-20260903.json`：微服务 3 轮逐请求原始结果；
- `raw-results/perf-comparison-pods-before.txt`、`raw-results/perf-comparison-pods-after.txt`：资源快照；
- `raw-results/perf-fixture-monolith.json`、`raw-results/perf-fixture-microservices.json`：等价数据集清单；
- `benchmark-config.example.json`：不含真实 Token 的配置样例；
- `create-performance-fixture.mjs`：通过 API 新建隔离的教师、学生、课程、作业和实验数据；
- `run-performance.ps1`：创建隔离 fixture、将 Token 只写入临时文件、采集资源并执行至少 3 轮；
- `performance-benchmark.mjs`：实际发压和计算 QPS/Avg/P95/错误率的脚本。

Compose 复测命令：

```powershell
./run-performance.ps1 -ResourceMode compose -Runs 3 -Concurrency 10 -RequestsPerTarget 30
```

Kubernetes 复测时指定网关地址并使用 `-ResourceMode kubernetes`。fixture 脚本不会修改全局选课阶段：窗口开放时使用学生 Dashboard/作业/实验概览接口；窗口关闭时在 manifest 记录 `enrollmentCreated=false`，并改用同一隔离课程的教师 Dashboard/课程作业/课程实验集接口。若提高到 50 并发或更大请求量，应先记录并统一网关限流配置；HTTP 429 必须计入失败，不能从报告中剔除。

# platform 组员同步进度指南

更新日期：2026-08-31。适用于 Windows / PowerShell。除特别说明外，命令均在项目根目录（能看到 `package.json` 和 `docker-compose.yml` 的目录）执行；每一步成功后再执行下一步，报错时不要继续粘贴后面的命令。

团队仓库：[Vesperx24/platForm](https://github.com/Vesperx24/platForm)。本指南统一以 `main` 作为同步分支，不要把旧的 `master` 或个人开发分支当成最新版本。

## 1. YAML 文件能上传，为什么队员还是不同步？

常见扩展名是 `.yaml` 和 `.yml`，不是 `.yalm`。GitHub Actions 的工作流使用 YAML，文件放在 `.github/workflows/` 下，支持 `.yml` 与 `.yaml`。GitHub 并不禁止上传这些文件，见 [GitHub 官方工作流说明](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)。

本项目核查结果：

- `docker-compose.yml`、`docker-compose.k8s-build.yml`、`.github/workflows/ci-cd.yml` 和 `k8s/` 下 10 个 YAML 文件，共 13 个文件，均已进入本地 Git 提交。
- 当前 `.gitignore` 没有忽略 `.yml` 或 `.yaml`。它主要忽略依赖、构建产物、真实环境变量、日志、测试输出及上传文件。
- 编写本指南前，本地 `main` 为 `bbca53a`，比本地缓存的 `origin/main` 领先 2 个提交。该比较没有刷新远程状态，不能直接当作 GitHub 实时状态；发布前应执行 `git fetch origin` 再核对。
- 刚整理的流水线证据仍是未提交文件；“文件已复制到 docs”并不表示“已经上传到 GitHub”。

文件同步需要经过完整步骤：**保存文件 → git add → git commit → git push → 队员 git pull**。已经跟踪的文件不受 `.gitignore` 新规则影响；新文件是否被忽略要看匹配规则，见 [Git 官方说明](https://git-scm.com/docs/gitignore)。

## 2. “完全同步”要核对四件事

| 同步内容 | 是否随 Git 拉取 | 队员需要做什么 |
| --- | --- | --- |
| 源码、锁文件、Dockerfile、YAML、数据库 migration、已提交的 docs | 是 | 拉取同一分支并核对提交 SHA |
| 新建但尚未提交的文件、未推送的本地提交 | 否 | 由作者提交、推送或通过 PR 合入 main 后再拉取 |
| `node_modules/`、`dist/`、Prisma Client | 否 | 按锁文件安装依赖、重新生成 Client，按需构建 |
| 根目录 `.env`、`backend/.env`、个人 AI 密钥 | 否，故意排除 | 从 `.env.example` 创建本机配置，自己填写敏感值 |
| PostgreSQL 中的业务数据、Redis 队列、Docker 卷 | 否 | 初始化自己的演示库；需要同一现场数据时另行安全移交 |
| `backend/uploads/`、容器上传卷中的附件 | 否 | seed 生成演示附件，或移交与数据库匹配的一套附件 |
| 本机 Docker 镜像、K8s 集群和 kubeconfig | 否 | 按需重新构建/拉取镜像、单独配置集群；普通开发无需 K8s |
| GitHub Actions Secrets、Environment、自托管 runner、运行历史与 artifacts | 不在 Git 文件中 | 在同一 GitHub 仓库查看，由负责人维护；fork 不会复制这些运行配置 |
| `test-results/` 和 `*.log` | 新文件默认忽略 | 提交前精选、脱敏后归档到 docs；已跟踪的旧报告仍可能随 Git 更新 |

**提交 SHA 相同只能证明提交内容一致。** 还要检查工作区修改、本机环境与数据库状态。不能要求所有组员直接复制组长的密钥、数据库密码或 kubeconfig。

## 3. 负责人先发布一个可同步版本

先检查当前分支、变更和远程进度：

```powershell
git branch --show-current
git status --short
git fetch origin
git log --oneline origin/main..main
git log --oneline main..origin/main
```

前一个 log 显示本地 main 独有提交，后一个显示远程 main 独有提交。如两边都有结果，先保留工作区改动、完成合并并验证；不要强制推送覆盖队友提交。

本次需要特别检查：流水线证据、本指南，以及中期检查里已有的图片目录移动和文档修改。图片重命名应同时提交旧路径删除、新路径新增和引用更新，不能只提交说明书。

本次新增材料和模板修正可按以下范围暂存（仅暂存这些路径，不代表处理了其它未提交工作）：

```powershell
git add -- "docs/组员同步进度指南.md" "docs/中期检查/容器化 + CICD流水线-llm/00-流水线证据索引.md" "docs/中期检查/容器化 + CICD流水线-llm/evidence" "backend/.env.example"
git diff --cached --stat
git diff --cached --name-status
```

逐项查看暂存内容，确认没有真实凭据、误删或不属于本次交付的文件，再提交：

```powershell
git commit -m "docs: add team sync guide and pipeline evidence"
```

该提交还只在本机。将所有计划交付的修改合入 main 后，负责人按仓库权限通过 PR 合并或推送 main。只有已确认当前位于 main、远程没有未整合提交、准备发布时才执行：

```powershell
git push origin main
```

**注意：本项目推送 main 会触发 CI/CD，部署阶段可能在生产配置齐全时执行。** 发布前由负责人确认环境。不要为了传文档随意推送部署标签或点击手动部署。

发布成功后核对并把完整 SHA 发给全员：

```powershell
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

确认两个 SHA 一致，并在 GitHub 的 main 分支查看本指南和证据目录。若远程被后续提交更新，重新明确团队要同步的版本。旧 `docs/中期检查.zip` 不会因为文件夹更新而自动更新；如交付压缩包，需重新打包并标注对应 SHA。

## 4. 组员拉取代码与文档

### 首次获取项目

先进入你自己的项目父目录，再执行：

```powershell
git clone --branch main https://github.com/Vesperx24/platForm.git
cd platForm
git rev-parse HEAD
```

仓库访问失败时，先确认登录账号已获得访问权限；不要向同学索取个人访问令牌。克隆后的 SHA 应与负责人通知的版本一致。若 main 已有后续更新，向负责人确认本轮同步版本。

### 已有项目、没有本地改动

```powershell
git status --short
```

确认没有要保留的未提交修改或未跟踪文件后：

```powershell
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git status --short
```

`--ff-only` 只允许快进更新；分支已经分叉时会拒绝拉取，避免悄悄生成合并。出现此类错误应先分析两边的提交，不要改用强制覆盖。参见 [Git pull 官方说明](https://git-scm.com/docs/git-pull)。

### 有自己的改动，或不确定怎样处理冲突

不要覆盖整个旧目录，也不要执行 `git reset --hard`、`git clean -fd`、`git push --force`。先把自己的工作保存在个人分支并选择性提交，敏感文件另行安全备份。

如果只想先拿到可演示版本，最稳妥的方式是在另一个目录全新克隆，保留旧目录原样。在项目父目录执行，且目标目录必须尚不存在：

```powershell
git clone --branch main https://github.com/Vesperx24/platForm.git platForm-sync
cd platForm-sync
```

旧目录中的工作后续再通过个人分支/PR 合入 main，不要把旧文件整包覆盖到新版本。Git 不会同步被忽略的本地文件，所以工作区干净也不代表本机没有旧 `.env` 或旧数据库。

## 5. 组员同步本地运行环境

以下主流程使用“本机 Node 运行应用 + Docker 运行 PostgreSQL/Redis”。与当前 CI 对齐使用 Node.js 24；需安装 Git、Node/npm，并启动 Docker Desktop。只阅读代码和文档可跳过本节。

### 5.1 准备本机配置

只在文件不存在时复制，避免覆盖个人配置：

```powershell
if (!(Test-Path -LiteralPath .env)) { Copy-Item -LiteralPath .env.example -Destination .env }
if (!(Test-Path -LiteralPath backend/.env)) { Copy-Item -LiteralPath backend/.env.example -Destination backend/.env }
```

分别编辑两份文件，注意它们作用不同：

| 文件 | 本机开发配置 |
| --- | --- |
| 根目录 `.env` | Compose 使用；默认 PostgreSQL `5433`、Redis `6379`。不要直接覆盖已有卷的数据库用户名、密码 |
| `backend/.env` | 本机 API 使用；`DATABASE_URL` 指向本机 `5433`，`REDIS_URL` 指向本机 `6379`，`CORS_ORIGIN=http://localhost:5173`，填写自己的 `JWT_SECRET` |

若根目录修改了映射端口或数据库凭据，后端连接串必须同步修改。例如 Redis 改为 `6380`，后端也应使用 `redis://127.0.0.1:6380`。Worker 会读取 `backend/.env`；额外的系统环境变量可能覆盖文件配置，已有环境请检查是否留有旧值。

AI 功能需要另外配置本人有权使用的服务密钥或本机模型服务。缺少这些配置时，拉取同一份代码也不代表 AI 功能可用。本次已清空模板注释中一处疑似真实密钥；如果旧值曾有效，持有人仍需在服务商后台撤销或轮换，Git 历史不会因本次编辑而清除。

### 5.2 启动数据库与安装依赖

先停掉本项目之前启动的 Node/Worker 终端，避免 Windows 占用 Prisma 文件。不要结束其他项目的进程。

```powershell
node --version
npm --version
docker version
docker compose config --quiet
docker compose up -d db redis
docker compose ps
```

确认 db、redis 健康后，按仓库锁文件安装，不复制别人电脑的 `node_modules`，也不删除锁文件：

```powershell
npm ci
npm ci --prefix backend
npm ci --prefix frontend
npm ci --prefix judge-worker
```

每条命令成功再继续。Node 版本、依赖下载或 Prisma 报错应先解决；不要把安装失败当成文件没有同步。

### 5.3 应用 migration 并生成客户端

确认 `backend/.env` 指向自己的开发库。数据库有重要数据时，先备份并查看新增 migration，再执行：

```powershell
npm run db:migrate
npm run db:generate --prefix backend
Push-Location judge-worker
npx prisma generate --schema=../backend/prisma/schema.prisma --generator judge_worker
Pop-Location
```

这里第一条是**根目录**命令，实际调用 `prisma migrate deploy` 应用仓库中已有的迁移。不要误在 backend 目录调用同名 `db:migrate`，那个脚本执行的是 `migrate dev`。生成失败时先恢复到项目根目录、解决错误再继续；Prisma Client 不应沿用旧版本。

**仅首次建立可丢弃的个人演示库时**，确认数据库和上传目录没有需要保留的数据后，才执行：

```powershell
npm run db:seed
```

**seed 会清空业务数据并重建演示数据/附件，不是每天同步必跑的步骤。** 禁止对共享库、生产库或需要保留的数据执行。演示账号：`admin@demo.local`、`teacher@demo.local`、`student@demo.local`，密码为 `Demo123456`，只用于本地演示。

若要求与组长“现有页面数据完全一样”，应由数据负责人另外安全移交同一时点的数据库备份与上传附件；不要靠重复 seed 恢复现场，也不要把数据库备份、用户数据或真实凭据推到 GitHub。

### 5.4 启动和验证

在项目根目录启动 API、前端与评测 Worker：

```powershell
npm run dev:full
```

保持该终端运行，打开 `http://localhost:5173`。另开终端检查：

```powershell
Invoke-RestMethod http://127.0.0.1:3000/health/live
Invoke-RestMethod http://127.0.0.1:3000/health/ready
```

两项应返回成功；再验证登录、课程内容以及一次实验评测。当前 Worker 执行 Python 使用 `python3` 命令，演示 Python 实验前需确认本机 `python3 --version` 可用；仅安装了 `python` 不一定足够。

### 使用完整 Docker 或 Kubernetes 的组员

- 完整 Docker Compose 是另一套运行方式，默认页面入口 `http://localhost:8080`。参考[现有操作手册](./中期检查/容器化%20+%20CICD流水线-llm/02-Docker-Compose操作手册.md)，将其中个人目录替换为自己的路径；拉取代码后需重新构建镜像，再启动。只执行 `git pull` 或重启旧容器不会自动更新镜像中的代码。
- 普通开发不需要复制组长的 Kubernetes 集群或注册自托管 runner。负责 K8s 的同学另按[Kubernetes 验收步骤](./李/2026-8-27/Kubernetes本地部署手工验收步骤.md)配置自己的环境，并以当前仓库 YAML 为准。
- 不要同时启动两套 API/Worker 指向同一个演示库和 Redis 队列，避免重复消费、端口冲突或测试互相干扰。
- 不要使用 `docker compose down -v` 解决同步问题，它会删除数据卷。

## 6. 日常同步后的验证和进度回报

每次开始工作：先保护自己的修改，再更新 main、核对 SHA；依赖或锁文件变更后重新 `npm ci`，schema/migration 变更后应用迁移并生成 Client，然后重启服务。功能开发使用个人分支，通过 PR 合入 main，合并后通知组员更新。

在自己的、已初始化演示数据的测试环境中，可依次执行：

```powershell
npm run build
npm run test:unit
npm run test:dao
npm run test:api
npm run test:e2e
```

运行 API/E2E 时保持 API 和 Worker 已启动。DAO/API/E2E 会操作测试数据，**不要针对共享演示现场或生产环境执行**。如使用完整 Compose/K8s，不可直接照抄这组本机测试命令，需另行对齐测试进程的数据库连接和 API 地址。

历史 2026-08-29 报告记录 45 条单元、4 条 DAO、15 条 API、10 条 E2E 通过；这只是历史证据，不表示队员当前机器已经通过。结果以自己的实际执行输出为准。

组员完成后在群里复制填写：

```text
姓名：
同步分支：main
提交 SHA（git rev-parse HEAD）：
工作区状态（git status --short；无输出则填“干净”）：

Node 版本：
数据库：个人开发库；迁移已完成 / 暂未验证
健康检查：live / ready
页面与实验评测：通过 / 失败 / 未测试
自动测试：实际结果或“未运行”
本轮完成的任务及文档路径：
阻塞问题（不贴密码、token 或完整 .env）：
```

负责人发布版本时同步发送：分支、完整 SHA、更新内容、是否需要更新依赖/迁移数据库、预期功能和已知问题。代码已推送、CI 已通过、部署已完成应分别报告，不能混为一个“已完成”。

## 7. 找不到文件时怎样排查

以当前流水线文件为例：

```powershell
git branch --show-current
git ls-files -- .github/workflows/ci-cd.yml
git ls-tree -r --name-only HEAD -- .github/workflows k8s
git check-ignore -v --no-index -- .github/workflows/ci-cd.yml
git status --short
```

`ls-files` 显示是否跟踪，`ls-tree HEAD` 显示是否已进入当前提交；`check-ignore` 有输出会指出匹配规则，没有输出且退出码为 1 表示没有匹配的忽略规则。不要仅凭 VS Code 文件颜色判断是否上传，也不要用 `git add -f` 整包强行上传被忽略的配置。

| 现象 | 优先检查 |
| --- | --- |
| GitHub 上没有新文件 | 作者是否 commit/push；网页是否切到 main；文件是否只在个人分支 |
| 本机看不到 `.github` | 用终端或编辑器查看隐藏目录；不要只手动复制可见文件夹 |
| 网页能看到 YAML，Actions 却没运行 | 文件是否在 `.github/workflows/`、触发事件是否满足、Actions 是否启用、有无权限限制；存储文件和执行工作流是两回事 |
| 部署任务排队 | 本项目要求标签匹配的 Windows 自托管 runner 在线；不是 YAML 没上传 |
| 文件一样但页面不同 | SHA、未提交修改、是否仍在运行旧进程/旧镜像、数据库内容、上传文件和本机配置 |
| 数据库正常但附件 404 | 数据库与上传文件不配套，不能只迁移数据库 |
| 5173 登录报 502/ECONNREFUSED | API 3000 是否启动、数据库/Redis 是否就绪 |
| 某些新 JSON/日志拉不到 | `test-results/` 与 `*.log` 默认忽略；查看已归档的 docs 或 Actions artifacts |

中期检查材料入口：[中期检查目录](./中期检查/)。流水线材料入口：[证据索引](./中期检查/容器化%20+%20CICD流水线-llm/00-流水线证据索引.md)，包含 29 份文件及 SHA-256 清单。该目录中的配置是检查时的快照，修改项目配置应修改根目录的实际源码，不要只改证据副本。

# 12 详细设计正文说明

## 1. 编写目的与适用范围

本章在总体架构、类清单、总类图和对象级顺序图的基础上，对系统设计进行连贯说明。重点回答四个问题：每个核心类承担什么职责，关键方法如何完成业务规则，类之间以何种方式协作，以及核心数据在系统中如何组织和流转。

系统采用 React + Fastify + Prisma 的前后端分离结构，并通过 PostgreSQL 保存业务数据、Redis/BullMQ 调度实验评测任务。源码主要使用函数、模块和 Prisma Model，而不是传统 Java 风格的业务 `class`。为满足面向对象详细设计要求，本文按运行期职责将其划分为以下设计对象：

- **边界对象（Boundary）**：React 页面和功能组件，负责人机交互、表单状态及结果展示；
- **控制对象（Control）**：Fastify 路由插件，负责认证、授权、参数校验和流程编排；
- **服务对象（Service）**：`backend/src/lib` 中的领域函数模块，负责可复用业务规则和算法；
- **实体对象（Entity）**：Prisma Model，负责持久化业务状态及对象关联；
- **基础设施对象（Infrastructure）**：Prisma Client、Axios、BullMQ、Worker、文件存储和 SSE 连接。

## 2. 分层职责与调用原则

### 2.1 表示层

表示层由 React 页面、Context、Hook 和功能组件组成。页面对象负责表达用户目标，例如 `EnrollmentPage` 表达选课意图，`CoursePractice` 表达组卷意图，`GradebookPanel` 表达教师查看和配置成绩的意图。页面不直接访问数据库，而是通过 `api:AxiosInstance` 调用后端接口。

`AuthProvider` 保存用户与 JWT，`CourseProvider` 保存课程上下文和多个课程子域集合。组件通过 `useAuth()`、`useCourse()` 读取共享状态，避免层层传递 Props。请求失败时，页面统一把后端错误转为提示；认证失效则由 Axios 响应拦截器清理会话并跳转登录页。

### 2.2 接口控制层

Fastify 路由插件是后端的应用控制器。每个控制器遵循统一处理顺序：

1. `authRequired()` 或 `optionalAuth` 解析身份；
2. Zod Schema 校验路径、查询和请求体；
3. 检查角色、资源归属或课程成员关系；
4. 调用领域服务或 Prisma 完成业务；
5. 将结果序列化为稳定 DTO；
6. 把业务异常映射为 400、403、404、409 等 HTTP 状态。

控制器不通过继承共享行为，而是依赖 `authGuard`、`courseAccess`、`enrollment-service` 等服务模块。Fastify 在 `index.ts` 中组合注册所有路由，形成单体应用的运行入口。

### 2.3 领域服务层

领域服务封装需要跨接口复用或容易出错的规则。例如：

- `EnrollmentService` 封装选课窗口、容量、候补和操作日志规则；
- `HomeworkStudentService` 根据多个字段推导学生作业状态；
- `LabSubmitService` 区分自动评测和人工评测，并决定是否入队；
- `PracticePickService` 根据 SMART、标签、错题本等模式选择题目；
- `GradeSummaryService` 区分教师与学生的作业成绩可见性口径；
- `CourseMaterialPolicy` 统一判断课程级、班级级和教师专属资料权限。

服务对象优先设计为无状态纯函数；确需访问数据库或外部资源时，通过单例 `prisma`、队列或通知总线完成。这样既适合当前单体，也便于以后迁移为微服务内部应用服务。

### 2.4 数据访问与基础设施层

Prisma Client 是统一仓储入口。实体关联、唯一约束和级联删除由 `schema.prisma` 定义；关键的多表一致性操作使用 `$transaction()`。文件内容保存在上传目录，数据库只保存安全化文件名、相对路径、MIME、大小及版本元数据。实验提交通过 BullMQ 解耦 API 与 Judge Worker；公告、资料和讨论通知通过 `SiteNotification` 持久化，并使用 SSE 触发前端刷新。

## 3. 核心类职责说明

### 3.1 用户、课程与选课域

`User` 是教师、学生和管理员的统一身份实体，`role` 决定角色能力。系统没有为三种角色建立继承子类，因为三者共享账户结构，差异主要体现在授权规则。`Course` 是课程聚合根，持有教师、学期、课程代码、容量、课表 JSON 和成绩权重，并组合教学班、选课、公告、资料、作业和实验等对象。

`Enrollment` 表示正式选课关系，`EnrollmentWaitlist` 表示候补关系，两者以 `(userId,courseId)` 保证唯一。业务状态不是存放在一个 `status` 字段里，而是由两类记录是否存在推导。`EnrollmentLog` 以追加方式记录 `ENROLL`、`DROP`、`WAITLIST_JOIN`、`ADMIN_ENROLL` 等事件，为管理端查询提供依据。`EnrollmentPeriod` 保存选课阶段和时间窗，是普通选课操作的前置门禁。

`EnrollmentService` 是该域的核心控制服务。`enrollStudent()` 依次检查时间窗、课程发布状态、重复选课和容量；`dropStudent()` 删除选课后调用 `promoteWaitlistForCourse()`；后者按 `createdAt` 选择候补队首，并在事务中创建正式选课、删除候补记录。管理员特殊加退课复用同一服务，只通过 `skipWindowCheck` 和 `operatorId` 表达授权差异，避免出现两套不一致规则。

### 3.2 公告、资料与通知域

`CourseAnnouncement` 保存公告正文、置顶状态和编辑历史；`AnnouncementRead` 与 `AnnouncementMark` 分别表达阅读和重要标记关系。教师发布公告后，`AnnouncementService` 查询课程选课名单并批量生成 `SiteNotification`。学生打开公告详情时，控制器同时 upsert `AnnouncementRead` 并更新对应通知的 `readAt`，保证课程公告和消息中心的已读状态一致。

`CourseMaterial` 保存资料元数据、目录、可见范围、目标班级、版本组和下载统计。`MaterialFavorite` 使用 `(userId,materialId)` 唯一键表达收藏关系。`CourseMaterialPolicy` 将权限判断集中为两层：先用 `canViewMaterials()` 判断能否进入课程资料域，再用 `materialVisibleToUser()` 判断某一资料是否对当前教学班可见。

资料上传由控制器解析 multipart，`UploadsService` 负责文件名安全化和物理写入，随后创建 `CourseMaterial`。更新资料时保留同一 `groupId`、增加 `version`，旧版本设为 `isCurrent=false`。下载操作在返回文件前再次执行权限与文件存在性检查，并更新下载次数和最后下载时间。

`SiteNotification` 是公告、资料、实验、作业、讨论和管理消息的统一通知实体。`NotificationEvents` 管理内存中的 SSE 客户端映射，业务写入通知后只发送“需要刷新”的轻量事件，前端再调用未读计数或列表接口读取权威数据。

### 3.3 作业与成绩域

`Homework` 保存发布、截止、迟交、重做、班级范围和评分策略。`HomeworkSubmission` 保存某学生当前提交状态，`HomeworkSubmissionVersion` 保存每次正式提交的历史快照。`HomeworkRedoRequest` 独立保存重做审批状态，避免把审批过程混入提交实体。

作业状态由 `computeStudentStatus()` 推导。它优先判断待审批重做、教师打回和正式提交，再结合草稿内容及截止时间返回 `NOT_STARTED`、`IN_PROGRESS`、`SUBMITTED`、`OVERDUE` 等状态。正式提交会锁定提交、写入 `submittedAt` 并创建版本；教师批改只写 `graded/score/feedback`，发布成绩再写 `released/releasedAt`，两步必须区分。

成绩聚合以 `Course.labWeight` 和 `Course.homeworkWeight` 为配置。`LabGradeService` 先求每道实验题最高分，再求实验集均分和实验总均分。`GradeSummaryService.computeHomeworkAverage()` 接受显式可见性参数：教师成绩册使用 `all-graded`，学生 `/grades/me` 与个人 CSV 使用 `released-only`。该设计修复了 `BUG-D1-LY-UC09-001`，未发布作业分数不再进入学生均分、总评和排名。

总评公式为：

```text
totalScore = (labAverage ?? 0) × labWeight
           + (homeworkAverage ?? 0) × homeworkWeight
```

当实验和作业均无有效均分时，总评为 `null`。系统按总评降序生成排名，并统计 `<60`、`60–69`、`70–79`、`80–89`、`90+` 和无总评人数。教师和学生使用同一公式，但学生成绩输入集合受发布状态约束。

### 3.4 实验、评测、练习与讨论域

`LabSet` 表示实验分组及统一时间窗，`Lab` 表示具体题目和评测模式，`TestCase` 保存输入、期望输出、权重和隐藏标志。`Submission` 是一次不可变历史意义上的提交尝试；重新提交创建新对象，而不是覆盖旧提交。

`LabSubmitService` 加载题目和实验集配置，检查时间窗、提交方式和打回配额。自动评测提交初始为 `PENDING`，创建后把 `{submissionId}` 投递到 `judge-submissions`；人工评测提交直接进入 `PENDING_REVIEW`。Judge Worker 消费任务后将状态改为 `JUDGING`，调用 `CodeRunner` 编译或执行代码，逐个运行测试用例并按权重计算分数，最后写入 `ACCEPTED`、`WRONG_ANSWER`、`ERROR` 或 `TIMEOUT`。

`PracticeSession` 是一次练习聚合，组合多个 `PracticeSessionItem`。`PracticePickService` 根据模式选择题目：SMART 参考历史薄弱项，WRONG_BOOK 读取未掌握错题，BY_TAG 根据知识标签筛选。学生作答时只更新题目项；提交会话后，`PracticeGradeService` 逐题批改并累计分数，同时更新题目统计。答错时创建或更新 `WrongBookEntry`，答对时移除尚未掌握的错题记录，最后把会话统一改为 `GRADED`。

`DiscussionPost`、`DiscussionComment` 和 `DiscussionAttachment` 组成讨论聚合。发帖和评论前使用讨论访问服务确认用户是管理员、任课教师或已选课学生。`MentionNotificationService` 对提及 ID 去重并排除作者本人，再创建 `DISCUSSION` 通知。匿名只影响显示作者，不改变数据库中的真实 `userId`，从而保留权限控制和追责能力。

## 5. 类间协作方式

### 5.1 同步请求协作

普通业务采用同步 HTTP 调用：用户操作边界组件，组件调用 Axios，Axios 把 JWT 交给路由控制器；控制器完成校验后调用服务和 Prisma，最后返回 DTO。该方式适用于需要立即得到确定结果的选课、资料收藏、作业提交、权重配置等操作。

### 5.2 数据库事务协作

必须“同时成功或同时失败”的写入使用 Prisma 事务。典型场景包括：

- 创建课程与写 `COURSE_CREATE` 日志；
- 候补晋升时创建 `Enrollment` 与删除 `EnrollmentWaitlist`；
- 正式提交作业时更新当前提交并创建版本。

通知一般在核心业务写入成功后生成。当前单体中部分通知仍与业务处于同一请求链；微服务拆分后应采用事务消息或 Outbox，避免跨服务部分成功。

### 5.3 异步队列协作

自动评测属于耗时、资源密集任务，因此 API 只负责创建提交和入队，Judge Worker 独立消费。前端通过轮询提交状态获得结果。队列消息只携带 `submissionId`，Worker 从数据库读取权威题目、代码和测试用例，避免消息体过大及数据版本不一致。

### 5.4 实时通知协作

公告、资料和讨论操作先把通知写入数据库，再通过 SSE 告知在线客户端刷新。SSE 事件不是最终数据源，即使连接中断，用户重新查询 `/notifications` 仍能获取完整通知。这种设计兼顾实时体验和消息可靠性。

### 5.5 文件资源协作

文件采用“数据库元数据 + 文件系统内容”的组合方式。控制器只接收合法 multipart；上传服务返回相对 `storedPath`；下载时根据相对路径解析绝对路径、检查存在性并创建只读流。数据库删除和文件删除需要同步处理，避免孤儿记录或孤儿文件。

## 6. 关键数据结构

### 6.1 身份与授权结构

```ts
type JwtPayload = {
  sub: string;   // User.id
  email: string;
  role: "STUDENT" | "TEACHER" | "ADMIN";
};
```

`sub` 是后端所有资源归属校验的用户主键。前端角色路由只提供导航保护，后端 `authRequired()` 和资源归属检查才是最终安全边界。

### 6.2 课表值对象

```ts
type ScheduleSlot = {
  dayOfWeek: number;
  periodStart: number;
  periodEnd: number;
  weekType?: "ALL" | "ODD" | "EVEN";
  room?: string;
};
```

课表以 JSON 持久化，但写入前必须经过 Schema 校验，读取后使用 `parseScheduleSlotsJson()` 还原。`slotsConflict()` 比较星期、节次区间和单双周，供选课冲突提示使用。

### 6.3 提交状态结构

实验提交状态直接持久化为：

```text
PENDING → JUDGING → ACCEPTED | WRONG_ANSWER | ERROR | TIMEOUT
人工评测：PENDING_REVIEW → ACCEPTED | WRONG_ANSWER
```

作业状态则由 `submittedAt`、`locked`、`graded`、`released`、`returnReason` 和重做申请共同推导。两种建模方式不能混用：实验强调异步 Worker 状态，作业强调多字段业务阶段。

### 6.4 成绩单元与可见性策略

```ts
type HomeworkGradeCell = {
  score: number | null;
  graded: boolean;
  released: boolean;
};

type HomeworkGradeVisibility = "all-graded" | "released-only";
```

`all-graded` 只用于教师成绩册；`released-only` 用于学生总览、个人 CSV、学生排名和分布。可见性作为显式参数传递，避免调用方无意使用错误口径。

### 6.5 通知结构

`SiteNotification` 的关键字段为 `userId`、`type`、`title`、`body`、`linkPath`、`readAt` 及可选业务外键。通知详情通过业务外键判断原对象是否删除，通过 `linkPath` 完成前端跳转。SSE 只传递刷新信号，不复制通知正文。

## 7. 一致性、安全与异常设计

### 7.1 一致性约束

- 数据库唯一键阻止重复选课、重复候补、重复收藏和重复公告已读记录；
- 事务保护课程创建日志、候补晋升和作业版本写入；
- 状态更新前重新查询资源，防止使用过期前端状态直接写库；
- 学生成绩汇总只读取已发布作业成绩，分项显示、均分、总评与排名使用同一口径。

### 7.2 授权约束

- 所有写接口必须校验登录身份；
- 教师操作同时检查 `course.teacherId`，不能仅检查角色；
- 学生课程资源访问检查 `Enrollment`；
- 通知已读操作按 `id + currentUserId` 查询，不能修改他人通知；
- 文件下载与列表使用同一资料可见性策略，避免“列表隐藏但直链可下载”。

### 7.3 异常映射

| HTTP 状态 | 适用场景 |
| --- | --- |
| 400 | Schema 失败、时间窗非法、文件过大、状态不允许 |
| 401 | 未登录、JWT 失效、SSE token 无效 |
| 403 | 角色越权、非课程成员、非资源所有者 |
| 404 | 课程、公告、资料、帖子或通知不存在 |
| 409 | 重复选课、课程代码冲突、容量冲突 |

错误响应统一返回 `{error:string}`，部分资源删除场景增加 `deleted:true`。前端应展示业务错误，不把所有 4xx 统一显示为系统故障。

## 9. 已知限制与后续改进

1. `User` 尚无启用/禁用状态，UC10 的账号状态管理未完整实现；
2. 管理员审计视图仍由 `SiteNotification(type=ADMIN_ACTION)` 拼装，缺少独立不可变审计实体；
3. 讨论提及后端只校验 UUID、去重并排除作者，没有再次校验接收人是否属于课程；
4. 文件内容与数据库元数据跨两种存储介质，尚无统一 Outbox 或补偿任务处理部分失败；
5. 缺失成绩分项按 0 加权、同分排名是否并列仍需由课程负责人确认并固化为契约测试；
6. 当前仍为模块化单体，目标微服务拆分时需要明确数据所有权和跨服务一致性方案。

上述限制必须保留在验收记录中；已修复的 `BUG-D1-LY-UC09-001` 需完成数据库/API 回归后再正式关闭。

## 10. 设计结论

系统核心设计以课程为业务入口，以用户身份和选课关系控制访问，以作业、实验和练习提交承载学习过程，以成绩聚合形成教学结果。前端边界对象只表达交互意图，后端控制对象负责安全与编排，领域服务集中业务规则，Prisma 实体保存权威状态。核心流程均已通过总类图和 10 张对象级顺序图表达，类职责、关键方法、协作方式和数据结构能够相互追溯。

# E - 单体与微服务性能对比复测报告

- 复测时间：2026-09-04
- 环境：同一台 Windows 主机、Docker Desktop Kubernetes、单副本
- 压测参数：并发 5、每接口每轮 100 次、5 轮、超时 10 秒
- 总请求量：单体 1500 次、微服务 1500 次
- 校验：所有响应均为 HTTP 2xx、`application/json` 且可解析为 JSON；错误率均为 0
- 统计口径：报告每个接口 5 轮结果的中位数

## 修正内容

旧压测存在三个会导致结论失真的问题：URL 组合丢失 `/api`、配置并发数没有被正确限制、全局列表接口受到两端既有数据量不同的污染。本次已修正为：显式保留 `/api`，使用固定数量的顺序 Worker 控制并发，并为两端分别创建一门课程、一份作业、一个实验集和一道实验题，通过课程 ID 访问定向接口。压测脚本还增加了 JSON 响应校验和零错误率门槛。

## 测试链路

- 单体：端口转发 → Legacy API。
- 微服务：端口转发 → Web/Nginx → API Gateway → Course、Homework 或 Lab Service。

这比较的是用户可见部署链路，不是纯函数或单个处理器的微基准。微服务侧多出 Nginx、Gateway 和跨服务调用，预期会有额外开销。

## 结论

在本次单机、单副本、低并发条件下，单体三个接口的中位 QPS 均更高，Avg/P95 均更低。微服务的 P95 相比单体分别高约 141.0%、86.2% 和 37.0%。这符合微服务增加代理转发、网络通信、鉴权和跨服务查询开销的预期。

结果不能外推为微服务在所有负载下都更慢。微服务的主要收益是独立部署、故障隔离和按热点服务横向扩容；要比较扩容后的容量，需要另做固定资源预算、多副本和阶梯并发实验。

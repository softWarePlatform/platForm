## 1. 目的

统一需求、用例、设计、代码和测试的编号方式，使每一项需求都能沿着“需求 → 用例 → 设计 → 代码 → 测试 → 结果证据”双向追溯。本项目实际技术栈为 TypeScript、Fastify、Prisma 和 Node.js，测试采用 Node.js Test Runner，由 `tsx --test` 执行。

## 2. 编号规则

| 对象 | 格式 | 示例 | 说明 |
|---|---|---|---|
| 需求 | `REQ-{两位序号}` | `REQ-01` | 与业务用例一一对应；后续新增需求顺延 |
| 用例 | `UC-{两位序号}` | `UC-01` | 既有文档中的 `UC01` 是兼容写法，新文档统一使用 `UC-01` |
| 系统顺序图 | `SYS-SEQ-{两位序号}` | `SYS-SEQ-01` | 对应一个主业务用例的系统交互 |
| 组件顺序图 | `COMP-SEQ-{两位序号}` | `COMP-SEQ-01` | 展开 Route、Service、Prisma/外部服务之间的调用 |
| 对象顺序图 | `OBJ-SEQ-{两位序号}` | `OBJ-SEQ-01` | 展开关键对象之间的协作 |
| 单元测试 | `UNIT-{用例号}-{两位序号}` | `UNIT-05-03` | 用例号固定两位，末尾编号在用例内递增 |
| API 测试 | `API-{用例号}-{两位序号}` | `API-05-01` | 对 Fastify HTTP 接口进行验证 |
| 端到端测试 | `E2E-{用例号}-{两位序号}` | `E2E-01-01` | 从用户入口验证完整业务链路 |

规则补充：

1. 编号一经写入追溯表不得复用；废弃项标为“已废弃”，不回收序号。
2. 同一测试覆盖多个用例时，选择主用例编号，并在追溯表备注其他关联用例。
3. 测试名称须包含编号，例如 `UNIT-07-04 空答案不能判为正确`。
4. 设计文件建议命名为 `{编号}-{简短中文名称}.puml` 或 `{编号}-{简短中文名称}.md`。
5. 测试结果只使用“通过、失败、阻塞、未执行”四种状态，并附执行命令或日志位置。

## 5. 执行命令与 CI 接入

8 月 26 日可直接交给 CI 负责人使用的阻断命令：

```bash
npm ci --prefix backend
npm run build --prefix backend
npm run test:unit
```

三个命令任一返回非零退出码，流水线应立即失败。根目录 `npm run test:unit` 已转发到后端单元测试；当前 GitHub Actions 工作流已调用该命令。

服务和数据库就绪后，可继续执行现有自动化脚本：

```bash
node scripts/step5-api-test.mjs
node scripts/step6-system-test.mjs
npm run test:integration
```

后面三项依赖可运行的数据库及服务环境，不计入 8 月 26 日纯单元测试的通过条件。
